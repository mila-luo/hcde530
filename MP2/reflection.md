# MP2 Reflection

## What did you build?

ResearchFlow is a three-phase web application that supports UX researchers through the full arc of a qualitative interview session. In the Setup phase, a researcher enters a research topic and optional starter questions; an AI model generates 8 follow-up questions focused on uncovering participant motivations rather than surface-level responses. In the Interview phase, those questions are displayed alongside a live notes panel and a session timer, so the researcher can stay focused on the conversation instead of logistics. Notes auto-save to localStorage on every keystroke. In the Affinity Board phase, the researcher pastes their session notes and the AI clusters the content into themed sticky notes with supporting quotes pulled directly from the notes. The researcher can then edit theme labels and quotes inline, delete themes that don't hold up, and add new ones manually. The tool is built in React with Tailwind CSS, uses the OpenRouter API for AI inference, and is deployed at hcde530.vercel.app.

## What decisions did you make?

The biggest scope change from MP2a was removing audio transcription via Whisper. The original plan included uploading an audio file, transcribing it via OpenAI Whisper, and feeding the transcript into Claude for theme generation. In practice, Whisper requires a paid OpenAI account and adds a server-side processing step that was out of scope for a two-week React project. I cut it and replaced it with typed/pasted notes as the input — same research outcome, significantly less risk. I also shifted from the Anthropic API to OpenRouter's free tier after discovering Anthropic requires a minimum $5 deposit for new accounts. OpenRouter routes to available free models and required only a 10-line change in the integration file. The platform stayed Cursor + React throughout — two external API integrations and an interactive affinity board with CRUD operations were past what Bolt or Lovable handle cleanly. I also designed in Figma before writing any code, which made every Cursor prompt more precise and prevented layout decisions from being invented in code.

## What would you do differently?

I would add a text area for notes directly on the Affinity Board page rather than relying on notes carried over from the Interview page via localStorage. In the current flow, if a researcher skips the Interview view and goes straight to the Affinity Board, the Generate Themes button has nothing to work with. A visible notes input on the Affinity Board itself would make the tool more flexible and less dependent on following the exact three-step sequence. I would also prompt the AI to return 2 quotes per theme rather than allowing variable output — some themes came back with 1 quote, others with 3, which made the sticky note cards visually inconsistent.

## What does this work demonstrate?

This project demonstrates competency across specification engineering, prompt engineering, AI integration, and interface design. The `.cursorrules` file is a working example of specification engineering — it defined file structure, component responsibilities, API rules, and explicit constraints before a single line of code was written, and every Cursor prompt referenced it. The two AI prompt chains show prompt engineering applied to a real research workflow: the question generation prompt produces motivation-focused questions specific to the entered topic (not generic placeholders), and the theme clustering prompt returns structured JSON that drives the UI directly. The OpenRouter integration in `src/lib/claude.js` — a single shared `callAI()` function with two exported methods, environment variable key management, and consistent error handling — reflects a clean, production-minded approach to AI integration. And the affinity board's inline editing, delete, and add interactions reflect the core HCD principle that AI output is a starting point, not a final answer.
