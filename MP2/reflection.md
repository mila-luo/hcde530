# MP2 Reflection

## What did you build?

ResearchFlow is a three-phase web application that supports UX researchers through the full arc of a qualitative interview session. In the Setup phase, a researcher enters a research topic and optional starter questions; Claude generates 6–8 follow-up questions focused on uncovering participant motivations rather than surface-level responses. In the Interview phase, those questions are displayed alongside a live notes panel and a session timer, so the researcher can stay focused on the conversation instead of managing logistics. In the Affinity Board phase, the researcher either pastes their session notes or uploads a recorded audio file — Whisper transcribes the audio, and Claude clusters the content into themed sticky notes with supporting quotes. The researcher can then edit theme labels inline, delete themes that don't hold up, and add new ones manually. The tool is built in React with Tailwind CSS and uses the Anthropic and OpenAI APIs.

## What decisions did you make?

The biggest scope decision was removing live in-browser audio recording in favor of file upload. Live recording is technically fragile — browser permissions, format inconsistencies, and API streaming complexity would have consumed most of the two-week build window. Uploading a pre-recorded file achieves the same research outcome with far less risk. I also cut cross-participant comparison from the MVP; the affinity board for a single session is more useful and completable than a half-built comparison feature. The platform choice — Cursor + React over Bolt or Lovable — was driven by the two external API integrations (Whisper + Claude) and the file upload flow. Both Bolt and Lovable handle simple UI interactions well but fight you when you need custom API pipelines. I also chose to design in Figma before writing any code, which meant the Cursor prompts were grounded in a real layout spec rather than invented in code.

## What would you do differently?

I would define the Claude prompt templates earlier and test them independently before building the interface around them. The question generation prompt went through several iterations before producing questions that felt genuinely motivation-focused rather than generic. Because I was building the UI in parallel, early placeholder questions set false expectations about the output quality. Separating prompt iteration from UI build would have saved time and produced a tighter interface. I would also add a simple participant label to each session so the affinity board could eventually support multi-session comparison — that one field would make the tool significantly more useful in a real research context without adding much build complexity.

## What does this work demonstrate?

This project demonstrates competency across specification engineering, prompt engineering, AI integration, and HCD problem framing. The `.cursorrules` file is a working example of specification engineering — it constrained every build decision and prevented scope creep across the two-week sprint. The two Claude prompt chains (question generation and theme clustering) show prompt engineering applied to a real research workflow, with structured JSON outputs that drive the UI rather than free-text responses that would require parsing. The API integration layer — routing all Whisper and Claude calls through dedicated utility files with consistent error handling — reflects a production-minded approach to AI integration. And the affinity board's edit/delete/add interactions reflect the core HCD principle that AI output should be a starting point for human judgment, not a fixed result.
